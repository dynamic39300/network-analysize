## 3. 关键决策记录

1. **先指南后工具**：先把环境机制（DNS 劫持翻墙）搞清写成指南，再据此实现检测规则，保证规则有依据；
2. **终端版先行、菜单栏版跟进**：CLI 快速验证检测/修复逻辑，再包装成常驻菜单栏应用；
3. **运行副本放 `~/Library/Application Support`**：因 launchd（gui 域）进程受 TCC 保护读不了 `~/Documents`（实测 `PermissionError: Operation not permitted`），故把可运行副本放非保护路径，项目源码目录只作开发源；
4. **UI 更新强制回主线程**：`AppHelper.callAfter` 是崩溃修复的固定范式，后续任何 UI 变更都必须遵守；
5. **launchd 检测防重复**：start 脚本先查 `launchctl print gui/uid/...`，避免 launchd 与手动实例并存；
6. **进程可见性**：菜单栏图标渲染依赖进程所属会话——**由 launchd gui 域启动的实例图标正常**；从隔离的沙箱/非用户会话进程创建的 NSStatusItem 不渲染（实测，详见下）。

## 4. 踩坑记录（2.0 必须规避）

### 坑 1：AppKit 主线程断言崩溃（已修复）
后台线程改 UI → `EXC_BREAKPOINT (SIGTRAP)` / "Must only be used from the main thread"。**规避**：所有 UI 变更经 `AppHelper.callAfter` 调度回主线程。

### 坑 2：TCC 保护导致 launchd 进程读不了 ~/Documents
launchd（gui 域）拉起的进程访问 `~/Documents` 直接 `Operation not permitted`，即使文件存在。**规避**：运行副本放 `~/Library/Application Support/`，源码目录只作开发源。

### 坑 3：iCloud 同步的 .venv 不可用（dataless）
项目目录在 `~/Documents`（iCloud 同步），`.venv` 文件为"未下载"状态，运行报 `OSError: [Errno 11] Resource deadlock avoided`（读 pyvenv.cfg 失败）。**规避**：安装副本的 venv 在本地非同步路径重建。

### 坑 4：菜单栏图标不显示（现象，根因未 100% 证实）
同一台机器上：launchd gui 域 + venv python 启动的实例图标正常（9月9日-11日公司电脑实测）；而从沙箱/非用户会话启动的进程（含原生 NSStatusItem 测试、pyobjc 测试、ObjC .app）图标不渲染，`statusItemWithLength_` 返回 `NSSceneStatusItem`（macOS 26 场景化对象）。**结论**：部署必须走 launchd gui 域 + 用户会话；2.0 需把"图标是否真的渲染"做成启动自检项。

### 坑 5：多实例来源混乱
同一项目存在多个启动入口（launchd / start 脚本 / .app 双击），进程管理状态（launchd `state=not running` 但旧进程仍在）易混乱。**规避**：统一由 launchd 管理，start 脚本只做兜底。

### 坑 6：自动修复 DNS 的连锁影响（9-12 事故）
20:17:52 应用自动把本机 DNS 切成公司 DNS（10.0.0.x）后，**所有依赖 DNS 解析的进程（含本工具运行环境）集体失联**——当时并非公司网络。**教训**：修复动作必须"场景感知 + 可回滚 + 修复前确认"，禁止无条件改写 DNS；这也是 2.0 的首要改造点。

# Relay 2.0 通用性改造方案

## 一、现状分析

### 当前硬编码清单

| 类别 | 硬编码内容 | 通用性问题 |
|---|---|---|
| VPN | 进程名 `UniVPN`、接口 `utun4` | 别人电脑可能用 Cisco AnyConnect / WireGuard / OpenVPN |
| 代理 | 进程名 `clash`、端口 `7890` | 别人可能用 Surge / V2Ray / Shadowsocks / 不用代理 |
| DNS | 公司 DNS `10.0.0.66/68`、公共 DNS `223.5.5.5/114.114.114.114` | 不同公司 DNS 不同，个人用户无"公司 DNS"概念 |
| DNS 规则 | VPN 连→公司 DNS，VPN 断→公共 DNS | 这是公司特定业务逻辑，个人用户不适用 |
| IPv6 | 硬编码禁用（AI 工具地域限制） | 不是所有人都需要禁用 IPv6 |
| 连通性 | 百度 / Google / OpenAI | 可配置，但当前写死 |
| Wi-Fi | 接口 `en0`、服务名 `Wi-Fi` | 部分 Mac 是 en1 或 AirPort |
| 修复动作 | DNS 切换 / 代理关闭 / IPv6 禁用 | 修复逻辑与检测逻辑耦合，不可扩展 |

### 核心矛盾
当前软件是"为公司特定网络环境量身定制的脚本"，要变成"通用工具"，需要将**环境特定参数**与**检测修复逻辑**分离。

---

## 二、改造目标

1. **开箱即用**：别人安装后无需改代码，自动识别环境并开始监测
2. **配置驱动**：所有环境参数通过配置文件定义，支持预设 + 自定义
3. **自动适配**：自动检测已安装的 VPN / 代理工具，没有的自动跳过
4. **一键修复**：修复动作可配置、可扩展，支持管理员权限提示
5. **可分发**：能打包成 .app 或安装脚本，一键部署

---

### 3.3 预设配置

内置 3 套预设，首次运行时让用户选择（或自动检测）：

| 预设 | 适用场景 | 关键配置 |
|---|---|---|
| `company` | 公司环境（UniVPN + ClashX + 公司 DNS） | VPN 启用、公司 DNS 强制、IPv6 禁用、连通性含 OpenAI |
| `personal_proxy` | 个人用代理翻墙 | VPN 禁用、代理检测启用、公共 DNS、连通性含 Google |
| `minimal` | 纯基础监测 | 只监测 Wi-Fi / DNS / 连通性，不碰 VPN/代理/IPv6 |

## 四、自动环境探测

首次启动时执行环境探测，生成配置：

### 4.1 Wi-Fi 探测
```bash
# 自动找到 Wi-Fi 接口
networksetup -listallhardwareports | grep -A1 "Wi-Fi\|AirPort"
# 自动找到 Wi-Fi 服务名
networksetup -listallnetworkservices | grep -i "wi-fi\|airport\|ethernet"
```

### 4.2 VPN 客户端探测
```bash
# 检查常见 VPN 进程
pgrep -fl "UniVPN|vpnagentd|wireguard|openvpn|Tunnelblick|Viscosity"
# 检查 utun 接口
ifconfig | grep utun
```

### 4.3 代理工具探测
```bash
# 检查常见代理进程
pgrep -fl "clash|Surge|v2ray|ss-local|Shadowsocks|trojan"
# 检查常见代理端口
lsof -nP -iTCP -sTCP:LISTEN | grep -E "7890|6152|1080|8080|1087"
```

### 4.4 探测结果 → 配置生成
根据探测结果自动选择预设并填充具体参数，用户可在菜单中修改。

## 五、检测插件体系

### 5.1 统一接口

```python
class BaseCheck:
    name: str           # 检测项标识
    enabled: bool       # 是否启用
    severity: str       # 默认严重级别

    def check(self, config: Config) -> list[Issue]:
        """执行检测，返回问题列表"""
        pass

    def fix(self, issue: Issue, config: Config) -> FixResult:
        """执行修复（可选，部分检测项无自动修复）"""
        pass
```

### 5.2 内置检测插件

| 插件 | 功能 | 可配置项 |
|---|---|---|
| WiFiCheck | Wi-Fi 连接状态、IP、SSID | interface、service_name |
| VPCheck | VPN 进程、隧道接口、假连接 | known_clients、company_dns |
| ProxyCheck | 代理进程、端口监听、代理残留 | known_clients |
| DNSCheck | DNS 服务器、混配检测、VPN 联动规则 | public_dns、company_dns、enforce_rule |
| IPv6Check | IPv6 状态 | should_be (on/off/ignore) |
| SystemProxyCheck | HTTP/HTTPS/SOCKS 代理开关 | 无 |
| ReachabilityCheck | 目标 URL 连通性 | targets 列表 |
| PortCheck | 关键端口监听 | ports 列表（可选扩展） |
| RouteCheck | 默认路由、VPN 路由表 | 可选扩展 |

### 5.3 问题模型

```python
@dataclass
class Issue:
    check_name: str       # 来自哪个检测插件
    issue_type: str       # 问题类型标识（用于匹配修复规则）
    severity: str         # high / medium / low
    description: str      # 人类可读描述
    suggestion: str       # 修复建议
    fixable: bool         # 是否可自动修复
```

## 六、修复引擎

### 6.1 修复规则匹配

修复规则与检测解耦，通过 `issue_type` 匹配：

```python
class FixEngine:
    def fix(self, issue: Issue, config: Config) -> FixResult:
        rule = config.fix_rules.get(issue.issue_type)
        if not rule:
            return FixResult(success=False, message="无对应修复规则")
        # 模板变量替换：{service} {company_dns} {public_dns}
        cmd = rule["command"].format(**config.template_vars())
        result = run_cmd_with_code(cmd)
        # 执行后自动验证
        return self._verify(issue, config)
```

### 6.2 修复后验证
每个修复动作执行后，自动重新运行对应检测项，确认问题已解决。如果未解决，记录失败并提示用户。

### 6.3 管理员权限
部分修复（如修改系统代理、DNS）需要管理员权限。修复引擎检测到需要 sudo 时，通过 `osascript` 弹出系统授权框，而不是在终端要求密码。

## 七、打包分发方案

### 方案 A：PyInstaller 打包 .app（推荐）

```bash
# 打包命令
pyinstaller --name Relay \
  --windowed \
  --icon app_icon_relay.png \
  --add-data "menubar_icon.png:." \
  --add-data "default_config.json:." \
  network-doctor-menu.py

# 产物：dist/Relay.app
```

优点：双击即可运行，不依赖 Python 环境
缺点：体积较大（约 50-80MB），需处理 rumps / PyObjC 依赖

### 方案 B：安装脚本（轻量）

```bash
#!/bin/bash
# install.sh
# 1. 检查 Python 3.9+
# 2. 创建 ~/Library/Application Support/Relay/
# 3. 创建 venv，安装依赖
# 4. 复制脚本和图标
# 5. 生成 launchd plist 并加载
# 6. 首次启动生成配置
```

优点：体积小，透明可控
缺点：需要命令行操作，依赖系统 Python

### 方案 C：Homebrew Cask（进阶）

创建 `relay.rb` cask，用户 `brew install --cask relay` 一键安装。适合正式发布。

### 推荐路径
1. 先用**方案 B**（安装脚本）验证通用性
2. 稳定后用**方案 A**（PyInstaller）打包 .app
3. 最终可考虑**方案 C**（Homebrew）分发

## 九、关键设计决策

### 9.1 为什么保留"公司 DNS 强制"逻辑？
这是当前软件的核心价值（VPN 连接时自动切公司 DNS，断开时恢复公共 DNS）。通用化后将其变为**可配置规则**：`enforce_company_dns_on_vpn`，公司用户开启，个人用户关闭。

### 9.2 为什么不自动修复？
自动修复有风险（改错 DNS 可能断网）。默认 `auto_fix=false`，用户手动点"一键修复"。高级用户可在配置中开启自动修复。

### 9.3 配置文件放哪里？
`~/.config/relay/config.json`，遵循 XDG 规范，不污染 Library。日志仍放 `~/Library/Logs/Relay.log`。

### 9.4 如何处理别人电脑没有 UniVPN？
VPN 检测插件设为 `mode: "auto"`，自动探测已安装的 VPN 客户端；如果没有任何 VPN，自动禁用 VPN 检测和 DNS 联动规则，只做基础监测。

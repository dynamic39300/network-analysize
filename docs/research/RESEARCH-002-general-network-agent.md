# Relay 通用网络诊断与工作流 Agent 研究

日期：2026-09-26。状态：研究与讨论提案，不是已批准的实施规格，也不代表功能已经完成。

> 后续共识更新：用户已确认“自主网络保障 Agent”方向，启用并授权后主动发现、诊断和修复问题，不依赖用户提问；执行能力可包含动态生成命令。下文保留为初稿，其中“只手动触发”和“仅选择固定动作”的建议已被更新。最新目标与待定边界见 [PRD-002](../product/prds/PRD-002-autonomous-network-agent.md)。当前运行代码仍为手动检测，本次仅记录产品共识。

研究方式：核对本地实现，抽样阅读产品官方文档、平台文档及 IETF 标准。未安装对比竞品，未进行跨平台兼容实测；厂商宣称的功能不是本项目的验收证据。本文区分来源事实、现有能力和设计建议。

## 1. 核心结论

建议定位：**面向个人复杂办公网络、可扩展到企业环境的跨平台网络诊断与安全恢复助手**。个人优先是本轮研究的工作假设，仍需用户确认，不是已经决定的市场方向。

“通用”应定义为能识别不同环境、说明证据与限制，并在受支持范围内安全处理，而不是对所有网络一律修改 DNS、关闭代理或重置网卡。应分别管理识别覆盖、诊断覆盖、修复覆盖和验证覆盖。

建议采用“本地可离线工作流 + 规则与证据模型 + 可选 AI 推理 + 受限权限执行器”。Agent 是一种编排方式，不意味着每一步必须调用大模型，更不意味着给模型 root/Administrator 后让它自由执行命令。

产品承诺应是：尽可能定位问题、恢复可控配置、验证结果并保留恢复手段。无法承诺修复断掉的网线、运营商故障、过期账号、公司拒绝的访问权限或远端服务停机；也无法保证系统设置回滚一定成功。

保留最新交互约束：**默认手动点击检测，不恢复后台周期扫描。** 工作流内部的有限复测、修复前后校验属于一次用户触发的会话。未来若需要持续守护，必须单独设计、明确选择开启，与本轮默认行为分开。

| [Cloudflare DEX](https://developers.cloudflare.com/cloudflare-one/insights/dex/)：围绕已注册客户端区分设备、网络、应用表现；[诊断日志分析器](https://developers.cloudflare.com/cloudflare-one/insights/dex/diagnostics/client-packet-capture/)可提供 AI 摘要与诊断事件。 | AI 解释与结构化遥测可以组合；仅有摘要不等于已执行修复，也不等于覆盖任意第三方 VPN。 |

样本支持的判断是：可观测性、应用体验、受控修复、厂商原生连接恢复是互补能力。没有据此证明存在能在所有个人与企业网络中安全自动修复一切问题的产品。

## 3. 通用化的基础模型

### 3.1 不再假设整台电脑只有一条网络链路

诊断对象建议是：`设备 + 用户/应用上下文 + 目标资源 + 预期策略 + 实际路径 + 采样时间`。

例如，同一时刻可能存在三种需求：公司内网经企业 VPN，普通网页直接连接，某个开发工具使用应用自己的代理。DNS 的域名分流、代理选择与路由会相互影响，不宜画成适用于所有请求的唯一线性链路。

UI 可以保留简洁的阶段编号，但底层需要依赖图。先获取基本环境，再按目标推导所需检查；互不依赖的只读探测可以有限并行。互相影响的修复必须串行执行，并在每次更改后重建受影响的证据。HTTP 代理访问还应拆开“电脑到代理”和“代理到目标”，不可把后半段推断成直接观测。

### 3.2 用正交维度覆盖组合，不堆“场景编号”

| 维度 | 至少需要表达的差异 |
| --- | --- |
| 平台 | Windows/macOS、系统版本、权限、受管状态、能力是否可读/可改 |
| 接入 | 有线、Wi-Fi、USB 网卡、热点、多个同时活动的接口 |
| 地址 | DHCP、静态地址、IPv4、IPv6、双栈、IPv6-only/NAT64 |
| 路由与隧道 | 无 VPN、全隧道、分流、按应用、多个隧道、重叠网段 |
| 名称解析 | 自动/静态、域名作用域、公司内部域、应用加密 DNS、hosts |
| 代理 | 无、HTTP CONNECT、SOCKS、PAC/WPAD、认证、应用单独配置 |
| 身份与策略 | 门户登录、802.1X、证书、VPN 身份认证、MDM/GPO、安全客户端 |
| 目标与症状 | 所有网站、内网、单一应用、偶发断开、慢、上传失败、实时通信失败 |
| 变化与归属 | 睡眠唤醒、漫游、网络切换、配置由 OS/用户/VPN/管理员谁管理 |

这是一份待实现的覆盖清单，不是当前支持声明。每个版本发布明确的组合支持矩阵；未覆盖或证据不足显示“未确认/暂不支持”，不要当作正常，更不要试探性修改。

### 3.3 预期状态不能只靠模型猜

建议建立“连接档案”，按能力组合，避免只能三选一：

- 目标资源：公众网站、公司域名、业务系统；明确需要哪些资源可用。
- 路径意图：哪些必须经过 VPN/代理，哪些应由系统选择；是否允许对照直连。
- 解析意图：内部域应由谁解析；敏感内部域禁止发送给公共解析器做对照。
- 设置归属：手动设置、网络下发、VPN 管理、企业策略；未知归属默认不写。
- 允许动作：可变更字段、权限要求、已知正常值、已审核恢复动作。
- 不可破坏的能力：公司内网、当前远程支持连接、已正常的目标、隐私约束。

可信优先级建议：受管设备的已验证管理员策略约束在先，用户意图不得绕过它；其后结合厂商声明、当前观测与同一网络上下文的已知正常记录。旧快照和 SSID 名称本身都不足以证明当前安全。推断的档案先标为候选，涉及修改时需要确认。

平台 API 与权限资料见 [跨平台能力附录](RESEARCH-001-platform-network-capabilities.md)。

## 4. 首批故障场景与动作边界

下表是建议的产品能力目录。动作都要求针对明确接口、作用域与策略，不能直接作为执行脚本。

| 场景 | 需要取得的证据 | 处理方向 | 不应自动做什么 |
| --- | --- | --- | --- |
| 有线无链路、Wi-Fi 未关联 | 实际活动接口、链路/关联、驱动状态 | 提示插线/选网；支持的情况下经确认重连 | 给未接通链路反复改 DNS |
| 有链路但无可用地址 | 地址来源、租约、网关、接口状态 | 对 DHCP 接口有条件续租；静态配置由档案或管理员确认 | 清空未知静态地址；自动配置任意 IP |
| 公共网络需登录 | 门户信号、跳转、目标测试，区分 TLS 异常 | 打开系统或可信入口，由用户完成认证 | 代填敏感凭据、接受证书警告、自动付费 |
| 多网卡/默认路径不符 | 指定目标的路由选择、接口标识、VPN 策略 | 优先解释实际选路；已批准策略下才更改 | 看见多个网卡就禁用其中一个 |
| 公网正常、内网异常 | 内部域解析作用域、VPN 状态/归属、到内部地址的路由 | 厂商支持的重连；恢复明确的分流档案 | 将全局 DNS 换成公共地址 |
| VPN 显示已连但业务不通 | 控制连接、数据路径、目标业务响应分别检测 | 限定厂商连接器，明确重连风险；必要时交管理员 | 仅凭进程名或 utun 存在判定 VPN 可用 |
| 本机代理残留 | 对应作用域的代理设置、本地端点、客户端归属、路径意图 | 恢复受信客户端或确认后关闭确属失效的本地转发 | 在必须经代理的环境中强制直连 |
| 远程代理/PAC/认证问题 | 对目标实际选出的代理、规则来源、认证状态 | 用户认证或恢复已批准配置；无法解析规则时保留未知 | 把 PAC 当成一条固定服务器地址；任意执行远端 PAC 代码 |
| 系统测试正常但某 App 不通 | 该应用代理/解析/信任上下文及可授权连接器 | 给出应用级修复或引导；缺少观测明确说明 | 以 curl 正常宣称应用一定正常 |
| IPv4/IPv6 一侧异常 | 分地址族的结果及实际应用路径 | 定位单侧异常、保留可用路径，按档案修复 | 把关闭 IPv6 当作通用优化 |
| 证书、时间或企业认证错误 | 系统时间、错误链路、认证状态、配置来源 | 时间明显异常时提示；证书和企业身份交受信流程 | 忽略 TLS 校验、安装陌生根证书、停安全软件 |
| 丢包/抖动/MTU/UDP 问题 | 有限时间多样本、实际目标、协议、包大小相关证据 | 定位可能环节；批准的切换或厂商配置调整 | 一次 ping 判定整条网络；默认跑满带宽测速 |
| 401/403/429/5xx | 传输与 TLS 已连通、实际 HTTP 响应 | 区分登录、权限、限流、服务故障，帮助联系对应方 | 重置本机网络并报告“修复成功” |
| 策略管理、网段冲突、多 VPN | 设置归属、目标路由、管理状态及冲突证据 | 尊重公司策略；输出问题位置和脱敏报告 | 与 MDM/GPO/VPN 客户端反复争抢配置 |

门户存在标准化发现机制，但并非所有部署都支持，且发现并不等于完成认证。[RFC 8910](https://www.rfc-editor.org/rfc/rfc8910.html)

双栈连接需要处理地址族差异与回退，不能把一次总成功当作双栈各路径都健康。[RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html)

大包黑洞、ICMP 信息缺失和隧道处理可影响路径 MTU 判断，因此性能诊断需要专门证据；本文没有建议自己实现完整传输协议栈。[RFC 8899](https://www.rfc-editor.org/rfc/rfc8899.html)

## 5. 推荐系统架构

```text
桌面交互：选择问题目标、检测、原因、处理预览、系统授权、结果
                              |
本地会话工作流：采集 -> 提出假设 -> 最小补充探测 -> 形成处理方案
           |                         |
           |                  可选 AI 分析/解释（非特权）
           |                         |
           +----- 确定性策略校验 <-----+ 仅返回结构化候选
                              |
                  用户确认 + 必要的系统授权
                              |
           本地受限执行器 -> 平台/厂商适配 -> 复检与恢复

旁路：证据记录、版本化动作目录、会话审计、恢复日志
云端：可选知识/模型/企业档案分发；不成为基本修复的必经路径
```

上图是逻辑职责划分，不要求拆成多个服务。第一阶段建议使用一个本地核心进程与按需的权限 helper，避免先引入分布式编排和大量 Agent。

官方工程资料将预定义代码路径的 workflow 与模型动态选择工具的 agent 区分，并提醒根据任务需要增加复杂度。这里借鉴的是边界划分，不是要求采用某家模型或框架。[Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### 5.1 模块与接口职责

| 模块 | 对外提供的小接口 | 内部承担的复杂性 |
| --- | --- | --- |
| 平台观测 | `observe(scope) -> EvidenceSnapshot` | 多网卡、解析作用域、路由、代理、管理状态，能力限制及平台差异 |
| 诊断工作流 | `diagnose(intent, snapshot) -> Diagnosis` | 依赖图、有限并行、缺失证据、假设排序、超时/取消、补充探测预算 |
| 计划与策略 | `plan(diagnosis, profile) -> RepairPlan` | 动作适用性、配置归属、风险、权限、与正常业务的冲突 |
| 受限执行器 | `execute(approved_plan) -> ExecutionResult` | 调用方认证、计划有效期、参数范围、写前校验、记录与恢复 |
| 验证 | `verify(plan, baseline) -> VerificationResult` | 原问题是否解除、关键目标是否退化、结果有效时间与未知边界 |

接口名称仅为讨论示例。先让 macOS 与 Windows 各完成一条实际链路，再确定公共接口；不要把 macOS 的命令名称原样包装成“跨平台接口”。两个适配都需要同样的领域语义，而不是同名命令。

### 5.2 AI 的适合位置

- 将“连着 VPN 但公司网页打不开”转成目标、症状和需要补充的问题。
- 从结构化证据提出候选解释，明确依据与缺失信息；不把概率口吻当作真实置信度。
- 在经过审核的只读探测目录中建议下一步，受时间、请求数量与隐私策略限制。
- 选择候选修复包并解释影响；不能自己授予执行许可。
- 将结果与已收集证据整理为用户可读说明或支持报告。

AI 不应接受任意 shell 执行工具，也不能直接更改路由、信任证书、防火墙或 VPN 配置。网络返回的页面、PAC、SSID、客户端日志都是不可信数据；其文字不得成为 Agent 的新指令。模型输出必须重新经过本地确定性校验。

本地保留规则、动作目录和恢复记录；云端不可达时，不允许“缺少 AI 回复所以无法回退”。本地小模型是后续可选优化，不是离线能力的前提。上传诊断数据需独立同意并最小化，敏感内部目标默认留在本机。

## 6. 权限与安全修复

### 6.1 两种同意，不要混为一谈

用户同意“修复这个问题”，解决的是产品意图；系统授权“允许这个受信进程执行这些操作”，解决的是 OS 权限。安装 helper 获准不等于以后每个修复动作都获准。

建议：普通诊断进程非特权运行；需要时才启用签名、可验证的本地 helper。helper 验证调用者与获批动作，不接受通用命令文本，不在网络端口暴露任意执行接口。Windows/macOS 分别采用本平台支持的服务/授权机制，详见平台附录。管理员权限不意味着可以绕过企业管理、安全策略、MFA 或 VPN 厂商能力限制。

### 6.2 风险分级

| 等级 | 例子 | 默认处理 |
| --- | --- | --- |
| 只读 | 读取地址/路由、对批准目标做有限探测 | 用户启动一次检测后执行，无额外提权；受流量与隐私预算限制 |
| 引导 | 打开系统设置、打开可信登录入口、重新测试 | 明确入口，不宣称自动修复 |
| 可逆设置 | 恢复已验证的某个服务 DNS、处理已确认失效的本机代理 | 预览具体范围、确认、必要时授权、保存原值、执行、复检 |
| 易中断动作 | 重连 VPN、续租 DHCP、重启网卡/网络服务 | 单独确认断网风险；策略批准后才执行，远程支持时更严格 |
| 不进入自动目录 | 绕过公司策略、关闭防火墙/EDR、忽略证书验证、安装未知根证书 | 说明原因、转交管理员；不是“高级一键优化” |

### 6.3 每个修复包必须定义完整闭环

`RepairPlan` 至少包含动作 ID/版本、平台能力要求、目标稳定标识、问题证据、配置归属、前置状态、拟改字段、所需权限、业务中断风险、验证目标、保护目标、恢复方案、过期条件。

执行流程：再次确认当前状态 -> 持久化必要恢复数据 -> 修改一个明确范围 -> 读取验证 -> 重新验证原问题与保护目标 -> 成功，或执行相应恢复/补偿并说明结果。

安全要求建议：

- 一个设备会话内不并发修改互相影响的网络设置；其他软件的更改也要检测。
- 获准计划绑定具体字段与值；状态改变必须重新评估，不能扩大原来的授权。
- 不因为整体得分提高就判定成功；“公网恢复但公司内网断了”应视为退化。
- 恢复只触及本次拥有的修改，避免覆盖 VPN/管理员刚写入的新状态。
- 配置恢复不等于网络恢复；两者分别显示结果。
- 非原子系统配置不能伪装成数据库事务；重连、DHCP 续租也不能承诺完全撤销。
- 崩溃与断网恢复要由本地机制处理；恢复日志、超时保护与中断恢复需要独立实现和测试，当前项目尚不具备完整能力。
- 定义重试上限、时间预算和停止状态，禁止无限“修复 -> 失败 -> 再修复”。

## 7. 用户体验示例

初始仍是紧凑首页，点击“检测”。可选一个问题范围：全部网络、公司资源、某个网站/应用；对未知环境优先自动只读识别，只问会改变处理方案的问题。

示例会话：

1. 用户选择“公司网页打不开”。
2. 展示“普通网页可访问；公司资源连接未成功”，不显示笼统“网络异常”。
3. 工作流核对目标域、VPN 路由及解析作用域；证据不足时只补充相关检测。
4. 若发现本机代理阻断且策略允许恢复，显示影响范围、拟执行动作和可恢复范围。
5. 用户点击“立即帮我处理”，必要时由系统请求权限。
6. 展示真实阶段：“保存原设置”“恢复指定设置”“复测公司网站”“确认普通网页仍可用”。
7. 明确给出“已验证恢复”“配置已恢复但连通性仍待确认”“需要管理员处理”等结果。

这是示例，不是对“公司网站打不开”的固定根因推断。同一症状也可能来自账号权限、分流规则或公司服务器，不能跳过证据直接执行上述动作。

应用诊断只有在具备对应连接器或用户提供可复现方式时，才能说验证了该应用。通用 HTTP 探针必须明确它只是代理指标。稳定性测试也应作为用户主动选择的有限观察会话，报告采样范围，不声称一次通过就保证长期稳定。

## 8. 当前项目可以复用与必须补齐的部分

依据本轮读取的工作区源码，不把历史提案当作实现：

| 当前能力 | 证据 | 下一步不足 |
| --- | --- | --- |
| 7 个检查项、分项结果与手动触发 | `code/relay/engine.py` 的 `DetectionEngine`；`code/network-doctor-menu.py` 的 `start/check/_periodic` | 当前依赖固定序列与共享状态字典，没有按目标的依赖图 |
| 证据不足时保留未知、区分 HTTP 与传输失败 | `code/relay/checks/vpn.py`、`reachability.py` | 仍不是应用真实路径的通用观测能力，PAC 路径标记未验证 |
| 类型化修复、快照、写前核验、复检和回退 | `code/relay/engine.py` 的 `FixEngine` | 动作窄、macOS 专属；没有完整的崩溃恢复或跨平台权限 broker |
| 检测器与 runner 可注入 | `code/relay/commands.py`、`checks/base.py` | 只是命令执行隔离，不等于已经抽象了 Windows/macOS 的领域差异 |
| 有线/其他接口的有限识别 | `code/relay/checks/wifi.py` | 多项配置仍以 `wifi.service_name` 为目标，多网卡/多服务不是一等对象 |
| 读取系统有效解析器 | `code/relay/checks/dns.py` | 当前汇总 nameserver 列表，没有完整保留每域的解析作用域与归属 |
| 原生交互、报告与脱敏 | `code/relay/panel.py`、`report_window.py`、`commercial/history.py` | 原始恢复文件不等于脱敏报告；Windows 桌面与安装授权链路待开发 |

`docs/07-通用性改造方案.md` 是重要历史思路，但其中固定场景、定时检测及 shell 模板不能直接成为新架构要求；当前引擎明确不执行历史配置里的任意 shell 修复模板。`code/relay_config.py` 存在此前已记录的本地兼容差异，后续实施前应单独确认，不在本轮研究中改动。

因此不是从零重写，而是把现有本地修复闭环逐步升级为领域模型、跨平台适配和受控工作流；暂不为了“像 Agent”先上复杂多 Agent 框架。

## 9. 建议推进顺序与验收

| 阶段 | 交付 | 退出条件 |
| --- | --- | --- |
| 1. 明确目标与支持矩阵 | 首批用户、典型目标、约 20 个优先场景、风险规则 | 每场景写清证据、允许动作、不可触碰设置、成功与失败含义 |
| 2. 跨平台只读骨架 | macOS + Windows 各跑通有线/Wi-Fi、目标选路、解析/代理作用域 | 同一领域模型可以表达两平台；缺失能力可解释，不把未知报正常 |
| 3. 少量可靠修复 | 先选 3–5 类高价值、可验证动作；平台权限与恢复机制 | 拒绝权限、断网、外部配置变化、部分写入、崩溃均有明确结果与安全停止 |
| 4. AI 辅助诊断 | 候选根因、下一步只读探测、自然语言解释 | 同一场景集对比规则基线，证明减少误诊/交互成本；模型不可达不影响基本功能 |
| 5. 厂商与企业扩展 | 有需求证据的 VPN/代理连接器、已签名组织档案 | 逐厂商逐版本声明支持；具备真实受管设备测试后才承诺企业能力 |

不在调研阶段拍脑袋承诺 Windows 全功能交付时间。系统版本、原生 UI、签名安装、提权、VPN 厂商接口和真实测试设备都会影响工作量。

## 10. 评估方法

- 场景库先包含正常复杂配置的负例，再加入真实故障。多个解析器、多网卡、多个隧道本身不能触发修复。
- 用组合覆盖压缩基础矩阵，再对高风险交互加专门用例；不能把组合采样说成穷尽所有网络。
- 使用可注入系统观测、命令记录回放、隔离网络/虚拟机和实机分层测试；虚拟机不能代替 Wi-Fi、USB 网卡、认证和原生授权实测。
- 单独注入权限拒绝、探测超时、休眠唤醒、目标掉线、计划过期、用户取消、外部软件改配置、修复中进程退出。
- 修复成功率的分母是“受支持且符合前置条件、获准执行的案例”，另报总案例覆盖率，避免以拒绝复杂案例美化指标。
- 关键指标：根因判断正确率、正常配置误报率、不当修复建议率、恢复成功率、回退/补偿成功率、正常业务退化率、定位时间与需用户操作次数。
- 未观察足够时间时只宣称“本次测试通过”。长时间稳定性需要有限、明确的观察窗口或用户另行开启的监测能力。

## 11. 下一轮讨论最值得决定的问题

先决定个人复杂办公网络还是企业 IT 管理优先，两者不应在首个版本同时做满。接着选一组最有价值的跨平台场景，确定“哪些自动处理、哪些先确认、哪些只诊断”，再冻结领域模型与首批修复包。AI 模型和编排框架的选型排在这些决定之后。

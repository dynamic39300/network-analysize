- **菜单栏版** = 面向日常使用的主界面（常驻、后台检测、图标状态、一键操作）；

- **DNS 守护** = VPN 状态驱动的 DNS 自动切换（独立于菜单栏应用，可单独启停）。

## 2. 检测模型

### 2.1 检测维度（菜单栏版 `NetworkChecker`）

| # | 维度 | 检测命令（核心） | 状态取值 | 判定要点 |
|---|---|---|---|---|
| 1 | Wi-Fi | `ifconfig en0` / `networksetup -getairportnetwork` | ok / error | 有 inet 地址即 ok |
| 2 | 公司 VPN | `pgrep -f UniVPN` + `ifconfig utun4` | ok / warning / off | 进程在但 utun4 无 IP = 假连接（high） |
| 3 | ClashX | `pgrep -f clash` + `lsof -iTCP:7890` | ok / warning / off | 进程在但端口未监听 = 异常 |
| 4 | DNS | `networksetup -getdnsservers Wi-Fi` | ok / warning / error | 依 VPN 状态判断公司/公共/混配 |
| 5 | IPv6 | `networksetup -getinfo Wi-Fi` | on / off | 启用即告警（泄漏风险，medium） |
| 6 | 系统代理 | `scutil --proxy` | on / off | 开启且 ClashX 未运行 = 代理残留（high） |
| 7 | 连通性 | `curl --noproxy '*'` 百度/Google/OpenAI | ok / error | HTTP 码非 000 即 ok |

### 2.2 DNS 判定规则（核心业务规则）

```
VPN 已连接(ok)：
  仅公司 DNS(10.0.0.66/68)          → ok
  混入公共 DNS(223.5.5.5 等)         → warning【DNS 混配，外网不稳定】
  无公司 DNS                         → error【未切公司 DNS】

VPN 未连接：
  含公司 DNS(残留)                   → warning【残留，解析可能失败】
  公共 DNS / 其他                     → ok
```

### 2.3 整体状态与问题分级

- 整体状态：`good / warning / error`（有 high → error；有 medium → warning；否则 good）；
- 问题分级：`high`（严重，优先修复）/ `medium`（警告）；
- 状态 → 图标：🟢 正常 / 🟡 警告 / 🔴 异常 / ⚪ 未知 / 🔄 检测中。

## 3. 修复模型（`fix_all`）

| 问题 | 修复命令 | 附带动作 |
|---|---|---|
| DNS 混配 / 未切 / 残留 | `networksetup -setdnsservers Wi-Fi <公司或公共>`（按 VPN 状态选择） | 清 DNS 缓存 |
| 代理残留 | `networksetup -set{web,secureweb,socks}proxystate Wi-Fi off` | 清 DNS 缓存 |
| IPv6 启用 | `networksetup -setv6off Wi-Fi` | 清 DNS 缓存 |

修复后自动触发一次重新检测（异步，延迟 1 秒），并用 alert 展示修复结果清单。

## 4. 菜单栏交互（rumps）

- 标题栏：emoji 状态 + 文本（如 `🟢正常`），点击展开菜单；
- 菜单结构：状态摘要（Wi-Fi/VPN/ClashX/DNS/代理/连通性/问题统计/最后检测时间）→ 分隔线 → **一键检测 / 一键修复 / 查看详细报告 / 关于 / 退出**；
- 每 30 秒后台线程检测一次（`CHECK_INTERVAL=30`）；
- **UI 更新全部经 `AppHelper.callAfter` 回到主线程**（崩溃修复范式，禁止绕过）；
- 一键修复有确认弹窗；退出提示自启仍生效及关闭方法。

## 5. 日志

- 菜单栏版：`~/Library/Logs/网络助手.log`（启动、每次检测结果摘要、修复动作、异常）；
- 终端版：项目目录 `network-doctor.log`；
- DNS 守护：项目目录 `vpn-dns-sync.log` + PID 文件。

## 6. 部署方案（当前基线）

```
安装目录：~/Library/Application Support/网络助手/
  ├── .venv/                       # /usr/bin/python3 创建，rumps+pyobjc+setproctitle
  └── network-doctor-menu.py       # 修复版（AppHelper.callAfter）

launchd：~/Library/LaunchAgents/com.wangxinlei.networkdoctor.plist
  ├── ProgramArguments = venv/bin/python + network-doctor-menu.py
  ├── RunAtLoad = true（开机自启）
  ├── WorkingDirectory = 安装目录
  └── stdout/stderr → ~/Library/Logs/network-doctor-launchd.log

加载：launchctl bootstrap "gui/$(id -u)" <plist>      # 必须 gui 域（用户会话）
卸载：launchctl bootout "gui/$(id -u)/com.wangxinlei.networkdoctor"
```

**部署约束（血泪经验）**：
1. 运行副本必须放非 TCC 保护路径（不能是 ~/Documents）；
2. 必须走 launchd **gui 域**启动（图标渲染依赖用户会话）；
3. venv 不能依赖 iCloud 同步路径（dataless 问题）；
4. 依赖版本：rumps 0.4.0、pyobjc-core/framework-Cocoa 11.1、setproctitle 1.3.7。

## 7. 已知薄弱点（2.0 改造输入）

1. 图标渲染可靠性无自检（曾出现"进程在跑但无图标"）；
2. 修复动作无场景感知、无确认回滚（9-12 事故）；
3. UI 依赖 emoji + alert 弹窗，信息密度低；
4. 检测串行执行（curl 超时累加，最坏 ~21s）；
5. 无通知、无历史记录/趋势；
6. 配置硬编码（公司 DNS、URL 列表、间隔）；
7. 打包发布依赖 py2app 手工构建，无签名/公证；
8. 多入口并存（launchd / start 脚本 / .app），进程管理易混乱。

## 实施顺序

1. 可靠本地任务：明确健康目标、固定方案、授权绑定、持久化记录、验证和中断核对。
2. 主动守护：用户启用、环境变化、预算、防抖、冷却、暂停及任务去重，接入原生总览。
3. 档案与跨平台：可信预期配置、环境适用范围、目标访问路径；Windows 平台采集和执行契约。
4. Agent 运行时：假设、追加探测、工具调用、模型适配、受授权约束的动态命令、离线降级。
5. 信任与产品体验：任务/持续授权、撤销、权限与隐私、厂商集成、完整导航、打包更新和跨平台实机验收。

这些是实施顺序，阶段退出条件仍采用蓝图 A–E。第一阶段的若干能力完成，不等于整个 C 阶段或整个产品已完成。

## 2026-09-27 后续交付：显式启用的 macOS 守护

F3 的首条纵向流程已贯通：原生开关 -> 保存启用选择 -> 变化订阅/低频检查 -> 预算内本地诊断 -> 形成方案与记录 -> 页面待确认 -> 用户确认后沿用成熟执行与验证。自动发现不占用修复确认门，也不会每次重复弹窗。同一事件仅通知一次，恢复后再出现异常会创建新事件。

`guard.py` 在独立调度线程工作，窗口关闭不取消已启用守护；`mac_events.py` 在自己的 CFRunLoop 中订阅 SystemConfiguration 变化。原生订阅不可用时明确显示仅定时检查。该模块仍和桌面在同一进程，不能替代 ARCH1 的独立本地核心生命周期。预算不足显示未完成检查，不把未探测目标判断为正常。旧的 `general.check_interval` 和 `auto_fix` 不会启用守护或赋予写权限。

实现依据：[Apple SCDynamicStore](https://developer.apple.com/documentation/systemconfiguration/scdynamicstore)、[PyObjC SystemConfiguration 回调约定](https://pyobjc.readthedocs.io/en/latest/apinotes/SystemConfiguration.html)。新增依赖已固定到现有 PyObjC 11.1，并加入打包隐藏导入；没有顺带改变其他依赖锁版本。

验证证据见 [QA-002](../../quality/reports/QA-002-diagnostic-panel.md)。本机只做过订阅注册/退出冒烟检查，没有人为切换本机网络，没有打开本机常驻守护；HTTP 响应体限制测试使用临时回环服务器。真实网络切换、热点耗电及 Windows 仍未验收。完整目标继续进行，下一项是 F2 健康档案和按目标/路径表达预期与观测。

## 2026-09-27 后续交付：网络健康档案

`profiles.py`、私有 SQLite 档案表及原生 `profiles_window.py` 已接入控制器、Agent、诊断和修复。建立/复制/修订/切换/移除、导入草稿及导出均有用户入口；工作线程处理持久化，活动修改与诊断/待授权修复串行。保存和启用是同一事务，修订需匹配旧版本。导入拒绝命令、授权、来源声明、既有验证结果和重复字段；用户确认后才使用。

探测结果绑定具体档案和目标定义，支持正常、退化、未知、过期、不适用和需认证。失败、路径未确认、范围未知、版本不匹配或过期结果不会更新最近正常记录。保存不修改系统配置，也不将实测 DNS/代理写成预期。授权及修复前提包含档案版本；服务成功变成需认证/重定向，或访问路径/适用条件/目标定义变化，均不能作为已验证恢复。

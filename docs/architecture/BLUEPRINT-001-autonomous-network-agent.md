# BLUEPRINT-001：NetCare 自主网络保障终局蓝图

日期：2026-09-26；实施状态更新：2026-09-27。承接已确认的 [PRD-002](../product/prds/PRD-002-autonomous-network-agent.md)。用户已授权按本蓝图逐步实施并最终整体验收；具体技术候选仍需按验证结果选定。当前进度和未完成要求见 [实施与验收台账](../engineering/tickets/TKT-002-autonomous-agent-delivery.md)。

本文描述完整目标，不是已完成功能清单。当前已落地部分本地任务、macOS 显式守护、档案、模型调查/授权后续接及动态命令试用，成熟修复支持当前核心内的限定范围信任。源码和新构建 App 默认进入五页工作台，复用既有账号/历史并连接独立核心。普通用户服务、签名 XPC 与独立原生配置 helper 已有实现和开发验证，但真实 Developer ID/root 安装、命名服务注册、重启恢复和升级尚未验收或完成；开发 socket 仍不是签名认证。Windows 为只读核心，跨核心续接、动态效果/补偿、完整产品体验及真实效果仍有缺口，具体证据以实施台账为准。开发过程没有据此授权修改用户电脑的网络配置或开启其实际守护。

## 1. 以终为始：用户最终得到什么

2026-09-27 用户调整交付顺序与门槛：当前先完成 Mac 版本，Windows 后续可选，时间成本过高时可取消。因此下文跨平台是保留的产品愿景，不再是当前 Mac 交付的阻塞项；其余 Mac 功能、安全、体验与真实场景验收要求不变。

用户在 Windows 或 macOS 上安装 NetCare，完成首次启用和授权。软件识别网络环境，建立可验证的健康目标，此后主动发现、诊断和处理连接问题。用户不需要先说“公司网页打不开”，也不需要复制命令。

日常的理想体验：正常时不打扰；问题出现时自主处理；超出授权或确实需要身份认证时才请求参与。用户随时能知道守护是否有效、保护了哪些连接、Agent 正在做什么、刚才改过什么，以及怎样暂停或恢复。

典型画面：用户从公司有线网络切换到家庭 Wi-Fi。NetCare 观察到环境变化，等待网络稳定后检查适用目标，发现某项残留设置确实阻断了应有的连接。Agent 调查原因，使用已有授权执行针对性修复，验证目标恢复并且其他受保护连接没有退化。首页留下简短结果，详细证据、命令和前后差异归入同一个处理事件。

这只是体验示例，不是固定诊断规则。网络切换、VPN 关闭、多个 DNS、多个接口本身都不能直接成为故障或修复依据。

### 终局不等于什么

- 不是必须开口交互的聊天机器人；对话是可选补充入口。
- 不是把所有红色检测项各自执行一遍修复的工具。
- 不是持续调用大模型或不停完整扫描设备。
- 不是自己承载全部用户流量的 VPN/代理；第一阶段不接管数据转发路径。
- 不是承诺物理线路、上游网络或外部账号问题都能本机修好。

### 产品成功的定义

优先衡量受保护目标的恢复时间、真实恢复率、正常环境误修率、修复引入的退化，以及每次事件需要用户参与的次数。分别公布受支持场景覆盖率，不通过排除复杂问题来美化成功率。不把执行命令数量、聊天轮数或全绿检测面板当作成功。

## 2. 功能架构：八组能力，一条闭环

| 功能组 | 主要 feature | 如何与其他能力组合 |
| --- | --- | --- |
| F1 环境识别 | 多接口、有线/无线、地址与路由、VPN/代理、解析作用域、系统和厂商能力、配置归属 | 产生带时间和来源的环境证据，供所有任务使用 |
| F2 健康目标与档案 | 应可访问的目标、预期路径、策略约束、配置来源、已验证正常状态、档案导入和切换 | 给“哪里不对”和“修好了没有”提供共同标准 |
| F3 自主守护 | 系统变化事件、适度探测、去重、防抖、冷却、暂停、资源与流量预算 | 从变化或健康异常创建处理事件，不把每次变化都当故障 |
| F4 Agent 诊断 | 症状归并、候选原因、主动追加检查、工具调用、动态计划、可选用户问答 | 根据证据决定下一步检查或处理，持续推进同一任务 |
| F5 授权与执行 | 逐次/任务/持续授权、成熟修复工具、动态命令、系统提权、取消与执行记录 | Agent 自己调用执行能力；授权不足时等待，获准后继续 |
| F6 验证与恢复 | 配置回读、目标访问复测、正常连接保护、恢复点、补偿、异常中断处置 | 决定任务成功、继续调查、恢复或交接，不能由命令退出码代替 |
| F7 事件与报告 | 当前任务、时间线、原因/证据/动作、前后对比、搜索、脱敏导出、支持交接 | 将多条检查组织成一件用户可理解的问题，而不是散落的日志 |
| F8 信任与维护 | 权限撤销、数据范围、云端 AI 选择、日志保留、版本更新、连接器能力、经验包审核 | 让长期守护有边界、可维护，并可持续扩展 |

标准组合：`F1 + F2 -> F3 发现 -> F4 调查 -> F5 执行 -> F6 验证 -> F7 留痕 -> 返回 F3`。F8 是全过程的支撑，不是单独走一次的步骤。

同一原因导致 DNS、VPN 和网页测试同时异常时，优先形成一个可解释的事件；只有有足够证据时才宣称共同根因。独立问题可以有独立事件，但影响同一配置的写操作不能互相竞争。

### 首次启用流程

1. 在普通主窗口完成环境只读识别，不强制先注册账号或连通云端。
2. 展示已识别的网络和候选保护目标，只询问无法可靠推断且影响动作选择的信息。
3. 选择守护与授权方式；明确应用授权、系统授权和数据上传同意是不同事项。
4. 建立第一份健康档案并开启守护；若网络已经异常，进入首次诊断，不能把坏配置学成正常基线。

公共基础目标可以来自经过维护的配置；企业内部目标来自可信企业档案或明确配置。应用目标发现只能使用获准的数据和受支持集成，不默认抓取所有流量、浏览记录或扫描整个内网。SSID 名称本身不能证明企业网络身份。

### 三种工作状态

| 状态 | 自动观察 | 自动诊断 | 执行修复 |
| --- | --- | --- | --- |
| 未启用/已暂停 | 不发起新的守护探测 | 可手动触发 | 仅处理明确发起的任务 |
| 守护中 | 是，按预算 | 发现异常后主动展开 | 按现有授权决定执行或请求授权 |
| 恢复/待参与 | 保留必要的现场信息 | 围绕当前事件继续 | 仅进行已获准步骤或必要恢复，不启动冲突修改 |

授权模式与守护开关分开：选择较高权限不等于自动启用守护，暂停守护也不等于强杀正在写入或恢复的动作。

## 3. 信息架构：三个业务视图，两个管理视图

| 一级导航 | 用户要解决的问题 | 核心内容 |
| --- | --- | --- |
| 总览 | 网络是否健康，有没有需要我处理的事？ | 守护开关、覆盖目标、当前环境、异常/待授权事件、紧凑检测清单、最近结果 |
| 处理记录 | 刚才发生什么，软件做了什么？ | 事件列表、执行时间线、证据、命令、前后差异、验证结果、恢复入口 |
| 网络档案 | 在这些环境里，哪些连接应该正常？ | 自动发现与已确认内容的区分、网络/目标/路径关联、配置归属、导入与修订 |
| 权限与隐私 | Agent 能做什么，数据会去哪？ | 授权模式、现有授权范围与到期、系统权限状态、撤销、云端数据范围、保留设置 |
| 设置 | 怎么管理这个软件本身？ | 开机启动、通知、版本更新、诊断目标维护、连接器、账号；不挤占诊断首页 |

不将“模型”“工具调用”“token”等实现概念放在普通用户首页。高级细节可以在事件详情与设置中查看。

### 事件详情布局

```text
返回处理记录       公司资源访问异常       正在验证      停止后续操作
原因：发现与当前路径不一致的配置；已收集对应证据
-------------------------------------------------------------
检测与处理时间线                 本次修改
检测到访问失败                   修改对象与字段
检查 VPN 和解析路径              原值 -> 新值
保存原配置                       授权依据 / 执行命令
执行获准修改                     恢复条件 / 恢复点
验证公司资源与普通网页
-------------------------------------------------------------
结果 / 尚未确认的部分            报告导出 / 需要时联系管理员
```

时间线展示实际执行事件、事实依据和简明决策理由，不生成虚假的进度百分比，不把模型猜测展示成已验证根因。正常结果不需要用户阅读完整对话。

### 授权与弹窗

普通处理进度使用页面内区域或详情侧栏，长报告保持非模态窗口。只有需要用户作决定的事项才使用短小确认 sheet；系统凭据由操作系统授权界面处理，不在聊天框或应用自制密码框收集管理员密码。

授权内容必须包含具体动作、影响对象、可能中断、恢复能力以及授权持续多久。动态命令可展开查看完整待执行内容；内容或目标改变时需要按授权范围重新评估。授权过期或网络上下文变化不能继续执行旧计划。

这一低打扰方向与 Apple 对 alerts 的建议一致：提示应克制、有行动价值，避免启动时仅为告知信息弹窗，也避免需要长篇滚动的 alert。[Apple Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)

### 暂停、停止、关闭

- 暂停守护：停止新增自动任务；当前修改到达安全停止点或必要恢复完成后暂停。
- 停止当前任务：停止后续探测和动作；已产生的配置更改不能因为关闭页面就消失，需要说明状态。
- 关闭窗口：隐藏界面，不隐式取消已经启用的守护。
- 退出/卸载：明确终止守护与辅助进程；正在写入时先进行安全收尾，不留下无人负责的高权限任务。
- 撤销授权：立即阻止未开始的新动作，对进行中的动作显示实际停止/恢复状态。

## 4. UI 品质基线

视觉方向是桌面工具：紧凑、安静、可扫描，延续现有 NetCare 标识。不是营销页，不做以聊天输入框或巨型健康分数为中心的首页。

| 设计项 | 建议约束 |
| --- | --- |
| 品牌与菜单栏 | 保留现有 Logo 和深浅色适配；菜单栏不恢复绿点/文字状态装饰，状态放入打开后的菜单或窗口 |
| 布局 | 侧栏 + 工具栏 + 无卡片包裹的内容区；列表分隔线组织信息，不堆套娃卡片 |
| 字体 | 系统界面字体；正文 13–14pt、分组标题 15–17pt、主标题 18–22pt；命令与地址使用等宽字体；支持系统辅助功能 |
| 颜色 | 系统背景、文字与强调色；成功/注意/错误用语义色，并同时配图标和文字，不只靠颜色 |
| 控件 | 守护用开关，模式用分段/单选，工具用图标和 tooltip，明确命令用文字或图标加文字 |
| 排序 | 待授权和正在处理优先；同一事件不拆成多个相似警告；列表更新不导致阅读位置反复跳动 |
| 进度 | 只显示实际阶段；未知耗时用阶段状态，不伪造完成百分比 |
| 详情 | 原因、影响、动作、结果逐级展开；不能让用户为了找处理入口先打开原始 JSON |
| 编号 | 只标真实步骤或执行顺序；并行分支明确分组，不伪装成唯一串行网络链路 |
| 窗口与适配 | 初稿沿用现有最小内容区域 760×560，默认窗口尺寸在原型阶段验证；长内容内部滚动，关键控制固定可见 |
| 可访问性 | 键盘导航、焦点、读屏名称、深浅色、高对比与减少动态效果；移动端不属于本轮桌面目标 |

UI 验收应覆盖首页正常、未知、检测中、自动处理中、待授权、权限拒绝、AI 离线、恢复失败和长报告，不能只验收一张正常状态截图。

## 5. 技术架构：本地执行为中心，AI 主导任务

```text
桌面 UI / 菜单栏 / 系统通知
               | 查询、订阅状态、批准/拒绝、暂停
               v
本地核心（普通权限）
  环境观测 + 健康档案 + 守护调度
               |
          事件与任务状态机 <------> Agent 推理运行时
               |                    选择检查、生成计划、调用执行
               v
       授权校验 + 执行协调 + 验证恢复
          |                         |
  普通权限工具                本地特权执行器（必要时）
          |                         |
       macOS / Windows 平台适配 + VPN/代理厂商适配

本地存储：证据、档案、任务、授权、执行收据、恢复记录
可选云端：模型调用、知识/连接器分发、账号、企业档案
```

这里 AI 是端到端任务的主动决策者，可直接调用执行工具；状态机不是代替 AI 作所有诊断决定，而是维护任务进度、授权、操作归属和恢复条件。也不需要“一个检测项一个大模型 Agent”：起步用一个主 Agent，多个可组合工具即可。

### 5.1 三种独立生命周期

1. 桌面界面负责交互，可以关闭重开而不影响已启用守护。
2. 本地核心负责持续守护、任务推进与状态持久化，必须脱离窗口事件循环独立工作。
3. 特权执行器处理确需更高权限的作业；安装/启用、调用鉴权、作业生命周期独立设计。

模型可以部署在云端或本地，但权限授权与执行进度的可信记录在本机。云端不直接开放远程 shell，不持有用户管理员密码。不同用户会话的观测和授权必须隔离，服务账户的网络结果不能被当成所有用户应用的实际结果。

### 5.2 核心领域对象

| 对象 | 关键内容 |
| --- | --- |
| EnvironmentSnapshot | 平台、稳定接口标识、网络上下文、配置归属、作用域、版本和时间 |
| Observation | 探测目标、实际路径、采集方式、结果、限制、有效期、原始证据引用 |
| HealthProfile | 应可访问的目标、预期路径、不可破坏的能力、可信来源及适用环境 |
| Incident / AgentRun | 问题范围、关联证据、任务阶段、假设与动作记录、预算、停止原因 |
| ActionProposal | 工具或动态命令、目标、拟改范围、权限、影响、前置条件、验证与恢复计划 |
| AuthorizationGrant | 授权人、范围、任务或期限、条件、撤销状态，与系统权限状态分开 |
| ExecutionReceipt | 实际执行内容与哈希、执行身份、开始/结束、返回结果、涉及的变更 |
| Verification / RecoveryRecord | 原问题与保护目标的测试结果、保存值、恢复过程、失败及剩余风险 |

不能继续以一个全局 `wifi/dns/vpn` 字典表达整台设备的所有路径。迁移时允许把现有结果转换成这些对象的有限子集，并明确哪些字段未知。

### 5.3 模块接口原则

| 模块 | 候选接口 | 必须隐藏并承担的复杂性 |
| --- | --- | --- |
| 平台观测 | `observe(scope)`、`subscribe_changes()` | OS 差异、多接口、域名/用户作用域、能力限制 |
| 任务管理 | `start_or_merge_incident(event)`、`pause(run)` | 去重、关联、并发、恢复中任务、取消语义 |
| Agent 运行时 | `advance(run, evidence, grants)` | 上下文管理、工具调用、缺失信息、模型失败与预算 |
| 执行协调 | `execute(proposal, grant)` | 权限、前置状态、进程、超时、写前记录、实际收据 |
| 验证恢复 | `verify(run)`、`recover(receipt)` | 目标与保护目标、可恢复/不可恢复动作、外部变更 |

这些名称用于讨论，不是现在要求实现的接口规范。优先用真实 macOS/Windows 差异验证接口，避免只有 macOS 实现时就猜出完整跨平台抽象。

## 6. 守护、Agent 与执行怎样协作

### 6.1 持续守护不是持续调用模型

普通本地观测负责发现变化。对网络切换、睡眠唤醒、VPN/代理状态变化等事件合并、防抖，先等待瞬态稳定；对受保护目标做有预算的探测。环境变化不自动等于异常，只有证据支持才创建处理任务。

同一问题重复触发要合并；恢复后的短期失败与长期稳定性分开统计。断网时降低重试频率，限制同时探测数量、模型调用、流量和总执行时间。大流量测速、抓包或更广范围发现需要独立范围与同意。

不预先承诺某个固定探测间隔或资源用量。先定义可测预算，在不同平台、供电状态、热点和 VPN 场景中验证，再确定默认策略。

### 6.2 任务状态机

```text
发现 -> 收集证据 -> 诊断 -> 制定方案 -> 检查授权
                                  |
                 已获准 ---------+-------- 待用户/系统授权
                    |
                  执行 -> 验证 -> 已恢复
                    |       |
                 未完成   仍异常/出现退化
                    |       |
              状态核对/恢复 <-+
                    |
             继续调查 / 等待参与 / 明确停止
```

每个转换都有事实或外部事件依据。模型响应结束不是任务结束，UI 关闭不是任务取消，命令成功不是网络已恢复。任务状态必须能在本地核心重启后核对，而不是默认从头再跑命令。

### 6.3 成熟工具与动态命令并行存在

成熟修复工具拥有明确参数、前置条件和验证方式，适合复用。动态命令通道允许 Agent 现场调查和处理未预置问题，不能退回为“只从固定动作列表中选择”。

两类通道都产生 ActionProposal 与 ExecutionReceipt，走授权、执行和结果验证。动态脚本的内容、调用身份与目标需要与获准内容绑定。计划变化、外部配置变化或权限撤销后必须重新核对，不照旧执行。

需要诚实承认：任意特权脚本的全部副作用无法靠静态分析、提示词或一次确认可靠推断。高信任模式扩大了用户允许 Agent 自主操作的范围，也扩大了风险；不能在允许广泛系统命令的同时声称系统严格保证只影响网络。

对未知副作用采用再次询问、收缩动作或停止，而不是依赖模型自报“低风险”。标准模式与高信任模式的具体默认边界留待单独确认；本稿不擅自把全面系统权限设为默认。

### 6.4 执行可靠性

- 修改前校验环境、目标身份和批准内容；防止把一份授权用到另一个网络或接口。
- 先保存必要恢复数据，再执行；可重复操作与不可重复操作显式区分。
- 进程超时不意味着它从未写入设置，必须回读和核对实际状态。
- 崩溃重启后先识别未完成作业；不能盲目重放具有副作用的命令。
- OS 配置不是原子事务；恢复或补偿可能失败，必须保留人工恢复信息。
- 发现其他软件更新同一字段时不覆盖其新状态，必要时交接处理。
- 在未知范围的写入过程中采用设备级串行协调；已证明独立的只读探测可以有限并行。
- 暂停或撤权阻止后续动作；当前动作与恢复如何收尾要可见，不承诺瞬间撤销已发生的修改。

### 6.5 离线与隐私

基础观测、已有修复工具、任务记录和必要恢复材料保存在本机。模型不可用时，可以继续已批准且可验证的本地恢复路径；需要新推理但没有可用模型时显示能力受限，而不是假装完整 Agent 仍可工作。本地模型是可选后续能力，不是唯一离线方案。

上传云端前按最小需要组织证据，内部域名、完整命令输出、代理凭据、原始快照和用户文件不能因为开启守护就默认上传。页面、日志、SSID、PAC 等外部内容仅是数据，不得成为赋权指令。

执行审计与用户可导出报告分开：原始恢复材料有访问控制和保留策略，普通报告脱敏。一次修复成功不能自动把动态脚本晋升为以后默认执行的经验包；需要回放测试、场景验证和版本管理。

## 7. 技术选型建议

### 当前推荐的演进路线

| 部分 | 建议 | 理由与待验证点 |
| --- | --- | --- |
| 本地诊断/Agent 核心 | 先保留 Python，并从桌面控制器中解耦 | 复用现有检测、修复和模拟测试；先证明领域模型与闭环，不全量重写 |
| 跨平台桌面 | 优先评估 Tauri 2 + TypeScript/React；不是本轮最终选型 | 共用界面与状态协议；原生授权、托盘、辅助进程生命周期及无障碍仍需两平台实测 |
| 系统适配与提权 | macOS/Windows 各自独立适配与安装授权实现 | 特权进程可以使用适合原生系统集成的实现；语言、最低版本和分发渠道以验证结果决定 |
| 本地持久化 | SQLite 保存任务/结构化证据，受保护文件保存必要恢复材料 | 便于本地事务与重启核对；保留期限、敏感字段及安全删除不能省略 |
| 进程通信 | 带身份校验、版本与请求 ID 的本地 IPC | 不向公网开放执行端点；UI 只发领域操作，不直接持有通用 shell 权限 |
| AI 集成 | 一套模型适配接口、一个主 Agent 运行时 | 支持云端和未来本地模型；工具调用日志可回放；暂不绑定复杂多 Agent 框架 |
| 云端 | 保留 Django 账号/商业后台，按需加入模型网关与知识分发 | 账号故障、订阅到期不能中断当前恢复；企业控制台不是首期前提 |

Tauri 官方支持随应用分发外部二进制，包括 Python 打包产物，因此保留现有核心并评估新桌面壳有官方机制可参考。这不代表 sidecar 会自动成为可独立常驻的守护进程，生命周期需要单独实现。[Tauri Sidecar](https://v2.tauri.app/develop/sidecar/)

Tauri 的窗口/命令能力控制可用于约束 UI 到本地核心的调用，但不能替代 macOS/Windows 提权或特权作业授权。[Tauri Capabilities](https://v2.tauri.app/security/capabilities/)

双原生 UI 是保留选项：若早期验证表明共享 UI 无法满足可访问性、资源预算或平台体验，再评估分别使用原生界面。不要为了复用 UI 而把浏览器渲染进程变成高权限执行器，也不要让更换 UI 成为完善诊断模型的前置条件。

macOS/Windows 观测、VPN 归属及权限的官方研究依据见 [平台能力附录](../research/RESEARCH-001-platform-network-capabilities.md)。其未验证项仍然成立；本稿没有完成任何新增平台实测。

### 明确暂不选的复杂度

不以微服务、集群任务队列、图数据库、多 Agent 群组、自建 VPN 驱动或浏览器扩展作为第一阶段的默认依赖。模块可有清晰接口，但不等于每个模块都要单独部署一个进程或云服务。

| `code/relay/commands.py` | 明确的进程结果与超时 | 增加作业身份、取消、输出限制及审计；另建经设计的动态命令入口，不把配置字符串直接交给 shell |

| `tests/test_diagnostics.py` 等 | FakeMac、故障注入、并发与原生布局检查 | 扩展平台契约、任务重启、权限、状态漂移、模型错误和跨平台实机测试 |

此前记录的本地 `relay_config.py` 兼容差异应作为单独基线事项确认；不能在架构迁移时静默覆盖现有用户配置或未提交变更。保持当前可用版本，按纵向功能逐步替换。

## 9. 分阶段交付与退出条件

| 阶段 | 一个用户可感知的完整结果 | 关键退出条件 |
| --- | --- | --- |
| A. 产品与体验契约 | 看懂总览、知道软件正在保护什么、能理解处理与授权 | 首批场景、健康标准、权限模式、关键状态交互得到确认；不是只确认正常首页 |
| B. 跨平台只读守护 | 两个平台能发现环境变化并形成可解释事件，暂不自动改配置 | 正常复杂环境不误报；覆盖有线/Wi-Fi；UI 重开不丢任务；资源预算可测 |
| C. 可靠执行闭环 | 一类真实高价值问题能从发现到授权、修复、验证或恢复 | 至少一种安全修复贯穿 UI/核心/平台；权限拒绝、断网、崩溃、外部写入均有验证 |
| D. Agent 自主推进 | 无需用户提问，Agent 能追加检查并处理受支持问题；动态命令先受控试用 | 对比规则基线证明收益；正确停止；模型误判和指令注入测试；明确残余风险 |
| E. 高信任与广覆盖 | 已选择信任模式的用户减少逐次确认，扩展真实需求的 VPN/代理集成 | 按场景/平台/厂商版本发布支持矩阵；稳定性与恢复指标达标后再扩大默认范围 |

不等全部 UI 翻新后才验证执行，也不等“大模型接通”才补恢复机制。每阶段用少量真实场景贯穿整条链路。具体日程应在权限安装、Windows 实机及 UI 候选验证后估算，不在本稿承诺日期。

### 测试与发布不能省略的能力

正常复杂配置负例、场景组合、Windows/macOS 真机、VPN 厂商版本、权限拒绝、授权过期、任务重启、模型不可用、错误命令、配置竞态、恢复失败、短时网络抖动、用户暂停与卸载，都属于验证范围。

特权模块、连接器和更新包需要可信分发、完整性验证、版本契约与升级失败处置。运行任务期间不悄然替换执行逻辑；更新失败不能清除尚待使用的恢复信息。某次测试通过不等于所有系统版本兼容。

## 10. 本轮建议优先讨论的三个决策

1. 是否接受“紧凑总览 + 事件详情 + 网络档案”为主要体验，而不是聊天首页。
2. 授权默认倾向逐次确认，还是明确范围的任务授权；高信任作为显式选择保留。
3. 第一组验证场景与用户范围：个人复杂办公网络和企业受管网络先做哪一组，以及能提供哪些 Windows/macOS 实机环境。

推荐先确认这些体验与行为契约，再冻结实施规格和界面技术栈。产品目标已经清楚，下一步最需要的是把“自动保障网络”变成可演示、可验收的纵向流程。

# SPEC-012：Mac 中断配置恢复

2026-09-27。承接 SPEC-010/011，将普通核心的恢复快照与原生辅助服务的持久批次连接起来。支持同一构建下核心/辅助实例中断后重新审阅，不能据此恢复旧执行授权、模型同意或跨版本身份。实现使用匿名 XPC、内存配置和临时文件联测；真实 root 服务、SystemConfiguration 写入和发行身份仍待隔离环境验收。

## 目标与不变量

- 配置看起来正确，不足以解除未结清的系统批次。普通只读检测必须先取得匹配原方案、原 apply/restore 清单的辅助服务终态记录，再判断当前配置与网络。
- 恢复只允许引用原操作恢复原值，或者明确保留当前修改并复验；不重放原正向方案，不运行任意回滚文本。
- 用户重新确认后也不能覆盖第三方的新值、变更后的代理端点或重建的系统服务。无法读取时保持待核对。
- 配置恢复与网络恢复分开：`restored` 仅证明相关配置回到原值；`verified` 还要求原问题解除、受保护连接未退化及新鲜检查通过。辅助服务永远不声称 `network_verified=true`。

## 辅助协议

继续使用签名配对、内核 UID/audit session、nonce/实例及固定 JSON 协议。新增三个方法，不扩大原有字段权限。

1. `recovery_inspect {batch_id}`：只读核对。其他 UID 不得查询；原账号的新登录会话可以审阅。每个已开始操作必须匹配原始请求、可信 before 快照和准确系统目标，输出 original/desired/drift/unknown；没有 prepared 记录为 not_started，无需访问配置。完整协议配置与原生记录只留在服务内存，不投影到 UI。普通核心还提供准确原始 `requests` 清单；其额外的未受理封存规则见下文。
2. 活动批次只有当前持有客户端可立即恢复。另一客户端须等原租约墙钟/单调期限到期，或辅助服务实例已改变。旧客户端并不会因 UI 重连丢掉批次；新的恢复接管后旧 perform/end 被拒绝。
3. pending 审阅返回单次随机 review ID，绑定完整批次、每项私有配置与记录、当前客户端/UID/session/helper 实例和 300 秒单调期限。后来的审阅替换旧审阅；字段之外的配置变化也使旧审阅失效。
4. `recovery_apply {batch_id,review_id,choice}`：再次检查资格、当前完整快照及允许选项。接管身份和全批新的 restore ID 在任何恢复写入前持久保存。只对仍等于原 desired 的字段调用原生反向事务；已是原值或未开始项不写。不得沿用旧 apply ID 重新执行。
5. 恢复过程继续占有全局批次。每批最多 10 个可能写入的恢复尝试；只读收尾不耗用写入次数。通信丢失不重试、不清空未确认上下文。重新审阅现场可以只读完成已生效的恢复。
6. `recovery_end {batch_id,recovery_id}`：当前接管者只读核对原动作、原 restore 及历次恢复意图。全部一致后记录 restored/retained/not_started。保留原历史执行结果，只增加完成/核对元数据，不把旧的不确定结果改写为成功执行。

正常 `end` 也核对可能存在的恢复记录。若回退本身不确定，即使原字段看似恢复也保留批次，等待显式审阅；不能清空批次但遗留一个阻止后续操作的未知意图。

## 双份记录与崩溃顺序

辅助终态先保存至私有 `batch-<id>`，然后清空 `helper-control.batch`。每个历史记录含原清单、用户、结果和结束身份，可在后续新批次或重启后查询，不仅依赖最近一条 `last`。若进程在两次保存间退出，下次调用仅补齐控制元数据，不改网络。

新的普通批次在历史记录达到 1000 条时停止接纳；未受理证明可使用至 2000 条的额外空间，不会重新开放普通批次接纳。已有批次的完成及历史查询不受此接纳上限阻止。原生操作收据继续遵守 SPEC-010 的容量及权限/ACL 规则。安全保留清理与跨版本迁移尚未实现，不能删除 root 恢复目录绕过这些限制。

普通核心始终比对本地 snapshot 的动作、方案哈希、batch ID 和准确 apply/restore 清单。没有可信终态证明、仍 pending 或清单不符时，本地任务继续 `needs_reconciliation`。终态 not_started 不猜测“曾写后还原”；其他终态仍须只读核对准确目标和当前值。通过历史确认终态后，仅释放同一 batch ID 且原清单匹配的本地传输上下文，不影响另一项活动任务；无需重启核心即可发起新的明确授权任务。

## 未受理请求的证明

`begin` 请求可能未送达，或者辅助服务已受理但回复丢失。这两种情况不能仅凭普通核心超时区分。裸 `recovery_inspect {batch_id}` 查询不到记录时仍拒绝，不自动判定未执行。

带准确原始清单的 `recovery_inspect {batch_id,requests}` 可封存尚未受理的 ID。辅助服务在全局操作锁内先核验清单反向关系和 ID 唯一性，查验持久终态、活动批次及其预留恢复 ID，再扫描所有用户/会话的私有操作收据和终态清单。任何 ID 冲突、损坏/不安全文件、扫描失败、容量不足均不产生证明。原有 last 指向该 ID 但历史文件缺失也不视为未执行。

确认不存在已受理或已执行证据后，先持久保存完整清单绑定的 `not_started` 终态，再返回。以后迟到的同一批次 `begin` 被拒绝，重启后仍然有效。回复丢失时只查原证明，不重发修复。此过程仅写审计元数据，不读写系统网络配置，不清空或更改另一活动批次及其审阅。已受理的同一批次仍进入 pending 审阅流程，不能用此方法绕过租约或恢复确认。

`helper-control` 缺失时，仅完全新建的执行目录（除所有权锁外无其他文件）可以初始化；存在旧收据或未知文件则启动失败，不能把残留历史当作全新服务。此约束不是跨版本迁移或记录清理机制。

## 核心与桌面流程

处理记录 → 待核对任务 → 私有执行收据显示原值、现值、精确服务标识及不可恢复原因。恢复/保留为独立按钮，必须勾选本次授权；任意动态命令的人工说明仍是独立路径，不能借此清除系统配置批次。

Core 的 `receipt_review` 保留辅助 review ID 和完整清单，仅向桌面发送可读字段/选项。`confirm_recovery` 只接受原任务、收据哈希、核心审阅令牌、restore/retain 与明确勾选，不接受桌面自报的系统目标、原值或原生请求。

确认绑定客户端、核心实例、原任务、原收据、当前档案和五分钟期限，只用一次。写请求先记录去重 ID，再交给工作线程。线程持有运行时门与执行锁，并在恢复前、意图落盘后、网络复验后重新核对授权；取消、档案变化、收据变化或过期不能继续收尾。

本地恢复意图先落盘，才调用辅助服务。普通核心在批次仍占用时重新检测网络；保留现值未通过网络验证时保留原生批次与本地待核对状态，允许重新审阅后恢复原值。辅助只读 end 确认后，再按终态与当前证据更新原 AgentRun，内存任务同步，不覆盖或伪造历史执行收据。旧信任和模型调查上下文不会恢复。

桌面失联、忙、核心改变、窗口关闭或审阅过期会禁用按钮；服务端独立执行全部核验。打开审阅不写配置，不注册服务，不授予模型上传或持续信任。过期或现场变化后须重新打开审阅，没有后台重发。

## 验证边界

原生测试覆盖断线/重启、当前持有者与租约接管、审阅漂移、第三方字段、无法回读、未知恢复、终态历史与崩溃窗口。完整 UI → Unix IPC → Core → 原生匿名 XPC → 内存事务 → FakeMac 复验已贯通，包含取消、写前日志失败、错误清单/档案/收据、单次授权和失去回复后零重复提交。

这不是 root 命名服务、双真实账号、真实管理员批准/拒绝、MDM 或 SCPreferences 实网测试。动态命令副作用与设备级协调、跨核心模型/信任续接、受信任升级、首次启用/无障碍和真实场景仍是 Mac 整体目标的后续工作。Windows 保留现有代码，后续可选。
